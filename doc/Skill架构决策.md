# Skill 架构决策

状态：多 Skill 与按需加载已实现；保留 `designs.skill_md` 作为数据库升级兼容字段。

## v0.1：保留一份可选 Skill

v0.1 继续让每名学生编辑一份 `SKILL.md`，以降低公开课中的理解和操作成本。Skill 表示“当前任务适用时采用的方法”，不是固定角色、长期记忆或每轮必须执行的剧本。

- Skill 为空时，Agent 仍按 Soul 和通用能力正常回答。
- Skill 非空时，模型必须先判断当前任务是否匹配；不匹配时不套用。
- 装备工具只表示工具可用，不表示本轮必须调用。
- 当前把单份 Skill 放入 system prompt 是 v0.1 的兼容实现，不是最终的数据模型或选择机制。

## v0.2：多 Skill 与渐进披露

每项 Skill 包含：

- 稳定 ID、名称；
- 学生可理解的说明和触发条件；
- Markdown 正文；
- 启用状态、更新时间。

模型首轮只接收启用 Skill 的“稳定 ID + 名称 + 适用场景”目录，以及平台提供的 `load_skill` 工具。模型判断任务匹配后才通过该工具加载正文；不匹配时不调用。学生端上下文回执只在正文实际加载后显示 Skill，不把“可用”误写成“已使用”，也不展示隐藏推理。

学生端支持创建、切换、编辑、启停和删除多项 Skill；每名学生当前最多 12 项。教师详情与投屏读取相同的结构化 Skill 数据。`load_skill` 与普通 Tool 一样计入本轮工具调用上限，但它只读取当前学生、当前场次请求中已经过服务端过滤的内容。

现有 `designs.skill_md` 在数据库从 v8 升级到 v9 时转换为一项默认启用的“我的 Skill”，不丢失学生内容。多 Skill 仍按 `run_id + student_id` 隔离。

## 与其他概念的边界

- Soul：身份、价值取向和表达风格。
- Memory：经过确认、可纠正和删除的事实。
- Skill：任务匹配时采用的方法。
- Tool：由平台执行的受控外部能力。

优先级保持为：平台安全规则 > Soul > 当前任务相关 Skill > 可用 Memory > 当前对话。

## 教师端能力边界

教师按课堂场次决定平台允许提供哪些 Tool，学生只能从允许集合中选择。模型实际可见的 Tool 必须同时满足“老师允许、学生启用、服务端已注册”，不能只依赖学生页面隐藏选项。

Memory 的场次模式和 Tool 开关的完整设计、动态切换语义与实施顺序见 [Memory V2：自然形成、可控使用与实施计划](MemoryV2设计与实施计划.md#六教师端课堂策略)。

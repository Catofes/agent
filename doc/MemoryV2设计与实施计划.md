# Memory V2：自然形成、可控使用与实施计划

状态：分阶段实现中。Phase Policy 已落地；`adaptive` 已具备自然提取并直接生效的最小闭环。结构化类型、敏感度判定、合并/纠正、撤销和提取状态仍按后续 Phase 实施。

Memory V2 是对 [Memory MVP](MemoryMVP设计.md) 的渐进演化，不推翻 MVP 已经建立的场次隔离、学生控制、来源追踪和上下文回执。核心变化是：Memory 从“需要学生处理的候选收件箱”变成“Agent 在自然对话中逐步形成、轻量告知、随时可纠正的学生画像”。

## 一、问题与目标

### MVP 已经解决的问题

- Memory 与单个对话历史分离，可在同一课堂场次内跨对话使用。
- 默认关闭，学生可以查看、确认、编辑、删除和清空。
- 自动提取发生在主回答之后，失败不会阻塞对话。
- 只有确认过且与当前输入相关的内容才会进入模型上下文。
- 上下文回执展示本轮实际使用的 Memory，不展示隐藏推理。

### 当前体验的问题

- 每条候选都要求确认，把 Memory 变成了额外作业。
- 学生不知道怎样表达才容易被提取，容易退化为刻意说“请记住……”。
- 候选只追加，不理解同一事实的补充、纠正、冲突和过期。
- 关键词和中文二元词匹配容易漏掉语义相关但字面不同的内容。
- 异步提取错误静默，界面无法区分“没有值得记的内容”和“提取失败”。
- Memory 页签以候选状态为中心，而不是以学生能理解的“关于我”为中心。

### V2 产品目标

1. 学生用自然语言表达偏好、目标和困难，不需要记忆触发词。
2. 低风险、高置信度信息可以自动生效，并提供明确提示和一键撤销。
3. 不确定或冲突的信息才进入待确认状态，减少学生操作负担。
4. 新信息能够合并、纠正或替代旧信息，避免重复堆积。
5. 只在确实有帮助时读取 Memory，并向学生说明实际使用了什么。
6. 保持公开课需要的低延迟、低成本、场次隔离和隐私边界。

### 非目标

- V2 不修改模型权重，也不声称模型本身永久学会了学生信息。
- V2 首期不跨课堂场次复制 Memory。
- V2 首期不保存完整思维过程、模型推测或教师不可见的学生档案。
- V2 首期不引入独立向量数据库；规模和效果证明需要后再增加。

## 二、概念模型

Memory 不是单一列表，应区分三种上下文：

| 层级 | 内容 | 生命周期 | V2 首期 |
| --- | --- | --- | --- |
| 对话历史 | 当前 Tab 的完整多轮消息 | `conversation_id` | 保持现状 |
| 学生画像 | 偏好、目标、背景、持续学习需求 | 当前 `run_id + student_id` | 重点实现 |
| 近期经历 | 跨 Tab 的近期任务、阶段进度和事件摘要 | 有过期时间 | 后续阶段 |

Soul 是 Agent 的身份和表达方式，Skill 是任务匹配时采用的方法，二者不是学生 Memory。程序性经验和 Agent 自我反思也不应混入学生画像。

## 三、自然写入

### 3.1 学生不需要触发词

以下表达都可以触发后台判断：

- “公式太多我容易乱，能不能多画图讲？”
- “我这学期想把英语口语练起来。”
- “叫我小林就可以。”
- “我已经学过一元一次方程，但函数还不熟。”

“请记住”和“忘掉这个”仍然作为强意图支持，但只是可选的明确控制，不是正常写入的必要条件。

### 3.2 允许写入的学生画像类型

- `preference`：讲解、表达、练习或互动偏好。
- `goal`：跨多轮仍然成立的学习目标。
- `background`：对后续任务有帮助的非敏感背景。
- `learning_need`：需要持续照顾的知识基础或学习困难。
- `preferred_name`：学生主动提供的称呼。

不写入临时任务、一次性格式要求、答案内容、模型推测、系统指令、密码、密钥、联系方式、身份证件、精确位置、健康等敏感信息。敏感内容不是“转为待确认”，而是直接拒绝自动持久化。

### 3.3 提取器输出

提取模型使用结构化输出，不再只返回字符串数组：

```json
{
  "proposals": [
    {
      "operation": "add",
      "kind": "preference",
      "content": "更喜欢通过图示理解数学概念",
      "confidence": 0.93,
      "durability": "run",
      "sensitivity": "low",
      "evidence": "公式太多我容易乱，能不能多画图讲？"
    }
  ]
}
```

`operation` 支持 `add`、`update`、`supersede` 和 `forget`。提取器同时读取现有学生画像，用稳定 ID 指向被更新或替代的条目，避免每轮重复追加。

### 3.4 确定性写入策略

模型只提出建议，最终策略由平台代码决定：

- 低敏感、允许类型、置信度达到阈值且无冲突：自动设为 `active`。
- 含义不明确、置信度不足或与现有信息冲突：设为 `needs_review`。
- 敏感、无证据、属于临时任务或超出允许类型：拒绝写入。
- 用户明确纠正或忘记：优先执行，但仍经过身份、作用域和敏感信息检查。
- 所有自动变更必须记录来源回合和变更原因。

置信度不能单独决定安全性；类型白名单、敏感规则、长度和总预算仍由确定性代码强制执行。

### 3.5 合并与纠正

写入前将提案与同类型现有条目进行协调：

- 相同含义：更新来源、置信度和最后观察时间，不新增条目。
- 补充信息：合并为更准确但仍简短的陈述。
- 明确纠正：新条目生效，旧条目标记为 `superseded`。
- 无法判断的冲突：保留原条目并产生一项 `needs_review`。

例如“我喜欢简短回答”和“数学题希望详细推导”不一定冲突，可以合并成带场景的两项偏好；“叫我小林”和“以后叫我小雨”则应替换旧称呼。

## 四、读取与上下文注入

### 4.1 首期读取策略

学生画像规模小且总预算受限，首期采用两段式策略：

1. 确定性过滤：只保留 `active`、当前场次、允许类型且未过期的条目。
2. 相关性选择：结合类型、词语匹配、最近使用、重要性和当前任务选择最多 5 条。

首期先改进本地评分和类别规则，避免每轮增加一次模型请求。保留现有总 prompt token 上限作为硬限制。

如果真实课堂数据表明语义漏检仍明显，再增加以下二选一方案并通过评测决定：

- 对最多 30 条 Memory 使用小模型结构化重排；
- 引入 embedding 召回，并继续用元数据和硬规则过滤。

不因为“向量数据库是常见方案”就提前引入额外运维组件。

### 4.2 读取反馈

上下文回执继续记录实际注入的 Memory ID 和内容。学生界面默认使用简短表达：

> 本轮参考了：你更喜欢图示讲解。

展开后可以查看来源对话、记录时间以及进入当前回答的原因。没有读取时不需要反复显示醒目的空回执。

### 4.3 使用后的维护

每次实际读取后更新 `last_used_at` 和 `use_count`。这些字段只用于排序、清理和产品解释，不代表模型一定遵循了该 Memory。

## 五、学生端交互

### 5.1 轻量提示

自动写入成功后，在对话区显示非阻塞提示：

> 已了解：你更喜欢用图示理解知识。　`撤销`

提示不打断输入，不要求学生跳转到 Memory 页签。撤销操作必须立即使条目失效，并阻止仍在运行的旧提取任务将其重新写回。

### 5.2 “关于我”页面

左侧 `Memory` Tab 的内部标题改成“关于我”，按学生能理解的分类展示：

- 学习目标
- 讲解偏好
- 正在学习
- 需要注意

学生可以直接编辑、删除、清空或关闭 Memory。`needs_review` 单独显示为少量“需要确认”，不再作为页面主体。

### 5.3 临时对话

后续阶段可以为单个对话增加“临时对话”开关：

- 不从该对话写入 Memory；
- 是否读取既有 Memory 由产品设置明确区分；
- 临时状态在对话顶部持续可见。

首期仍以学生级 Memory 总开关为准，不在同一阶段增加两套容易混淆的开关。

## 六、教师端课堂策略

Memory 和 Tool 的可用范围由老师按课堂场次控制，学生只能在允许范围内选择，服务端负责最终强制执行。

### 6.1 Memory 模式

教师端不直接展示“V1/V2”这种开发版本号，而使用可理解的课堂模式：

| 内部值 | 教师端名称 | 行为 |
| --- | --- | --- |
| `disabled` | 关闭 Memory | 学生端不写入、不读取，并隐藏或禁用 Memory 编辑区；已有数据保留 |
| `review_required` | 确认后记忆 | MVP 行为；自动提取候选，学生确认后才能读取 |
| `adaptive` | 自然记忆 | V2 行为；低风险高置信度内容自动生效并可撤销，其他内容等待确认 |

教师选择的是本场次允许的最高 Memory 模式，学生仍保留个人开关。实际状态需要同时满足：场次策略没有关闭，并且学生主动开启。

新建场次时由老师选择模式；为了兼容现状，未显式设置的既有场次默认为 `review_required`。切换模式只改变后续行为，不删除已有数据：

- `disabled`：立即停止读取和新提取，保留条目。
- `review_required → adaptive`：既有已确认条目继续生效，既有候选仍等待处理。
- `adaptive → review_required`：既有 active 条目继续作为已经生效的记忆使用，后续新提案必须确认。

每次切换增加策略 revision。异步提取完成时必须重新核对 revision，防止旧模式下启动的任务在切换后写回。

### 6.2 Tool 提供范围

老师为本场次选择平台提供哪些 Tool，例如：

- 计算器
- 联网搜索（后续）
- 绘图（后续）
- 图片生成（后续）

学生设计中保存的是“我想启用哪些 Tool”，场次策略保存的是“老师允许哪些 Tool”。模型实际可见的集合必须是：

```text
effective_tools = student_selected_tools ∩ run_allowed_tools ∩ server_registered_tools
```

安全约束：

- 前端隐藏或禁用不等于授权，保存设计和执行 Tool 时都要在服务端校验。
- 老师关闭某个 Tool 后，后续模型请求不得再看到该 Tool；Agent 循环执行每次调用前也要重新检查策略。
- 已经保存的学生选择可以保留。老师重新开放 Tool 后，学生不必重新配置。
- 未配置的既有场次默认允许当前已经上线的 `calculator`，保证升级兼容。
- Tool 开关控制能力可用性，不代表模型每轮必须使用。

### 6.3 教师端交互

教师状态墙增加“课堂能力”卡片：

- Memory 模式单选：关闭／确认后记忆／自然记忆。
- Tool 多选：按当前服务端 Registry 返回的可用 Tool 动态展示。
- 显示当前策略更新时间和是否已经同步到学生端。
- 修改后明确点击“应用到本场次”，避免误触立即影响正在进行的课堂。

策略更新后通过现有学生 SSE 广播 `classroom_policy` 事件。学生页面立即更新 Memory 说明、开关状态和 Tool 选项；正在输入的内容不丢失。

新建场次对话框同时要求确认场次名称、Memory 模式和 Tool 列表。后续修改只作用于当前场次，不反向修改历史场次。

## 七、数据模型与接口演进

### 7.1 `memories` 增量字段

在现有表上通过下一版本 SQLite migration 增加：

- `kind TEXT NOT NULL DEFAULT 'background'`
- `confidence REAL NOT NULL DEFAULT 1`
- `importance INTEGER NOT NULL DEFAULT 1`
- `sensitivity TEXT NOT NULL DEFAULT 'low'`
- `evidence TEXT NOT NULL DEFAULT ''`
- `last_observed_at TEXT NOT NULL DEFAULT ''`
- `last_used_at TEXT NOT NULL DEFAULT ''`
- `use_count INTEGER NOT NULL DEFAULT 0`
- `superseded_by TEXT NOT NULL DEFAULT ''`
- `expires_at TEXT NOT NULL DEFAULT ''`

状态从 MVP 的 `candidate/confirmed` 演进为：

- `needs_review`
- `active`
- `superseded`

兼容迁移：既有 `confirmed` 转为 `active`，既有 `candidate` 转为 `needs_review`。API 在迁移期间可以接受旧状态，但响应统一返回新状态。

### 7.2 变更审计

新增 `memory_events`，记录 `added`、`updated`、`activated`、`superseded`、`forgotten` 和 `undone`。事件至少包含 Memory ID、来源回合、变更前后摘要、时间和触发方式。审计用于撤销、排错和课堂演示，不进入模型上下文。

### 7.3 异步任务状态

每次提取任务产生可观察状态：

- `extracting`
- `no_change`
- `changed`
- `failed`

状态通过学生事件流推送，页面据此刷新，不再依赖回答结束后固定延时轮询。失败写入服务日志和指标；学生端只显示不打扰主任务的简短状态。

现有 REST 路由继续保留，并扩展：

- `POST /api/memory/{id}/undo`：撤销最近一次自动变更。
- `GET /api/memory/events`：查看当前学生、当前场次的变更记录。
- `GET /api/teacher/policy`：读取当前场次的 Memory 和 Tool 策略。
- `PUT /api/teacher/policy`：原子更新当前场次策略并增加 revision。

新增 `run_policies` 表，避免不断向 `runs` 增加能力字段：

```text
run_id          TEXT PRIMARY KEY
memory_mode     TEXT NOT NULL
allowed_tools   TEXT NOT NULL
revision        INTEGER NOT NULL
updated_at      TEXT NOT NULL
```

学生的 `/api/design` 响应或单独的 capabilities 响应需要同时返回 `memory_mode`、`available_tools` 和最终生效状态；不能让前端自行猜测服务端策略。

## 八、隐私和安全边界

- Memory 仍默认关闭，学生显式开启后才进行写入和读取。
- 所有读写继续使用登录 session 中的 `run_id + student_id`，客户端不能指定其他作用域。
- 高敏感信息禁止自动持久化，不因学生确认而放宽首期规则。
- 提取输入视为不可信数据，不能执行其中的指令或改变安全策略。
- 自动写入必须可见、可撤销、可纠正、可删除和可清空。
- 教师端是否查看学生 Memory 需要单独产品决策，V2 首期不新增教师读取能力。
- 教师可以控制 Memory 模式，但不能因此直接读取某个学生的具体 Memory 内容。
- SQLite 服务端存储继续作为权威数据源。浏览器本地存储最多用于界面缓存和待同步状态，不能作为唯一副本。

## 九、分阶段实施计划

### Phase Policy：课堂能力控制

实现状态：已完成。教师端可按场次切换三种 Memory 模式和 Registry 中的 Tool；策略通过 SSE 同步学生端，服务端在模型请求与 Tool 执行前重新计算有效交集，并以 revision 防止旧提取任务跨策略写回。

目标：先建立老师对 Memory 模式和 Tool 能力的场次级控制，为 V2 灰度验证提供开关。

- 增加 `run_policies` migration、Store API 和 revision。
- 增加教师策略读写接口和“课堂能力”卡片。
- 学生 SSE 接收策略变化并刷新 Memory 与 Tool UI。
- 保存设计、组装模型请求和执行 Tool 三处都计算有效 Tool 交集。
- Memory 提取和读取统一检查场次模式与学生个人开关。
- 新建场次可以指定策略，既有场次使用兼容默认值。

验收：老师可以把同一个服务切换到 MVP 确认模式或 V2 自然模式；禁用计算器后，即使学生旧设计仍选中计算器，模型也看不到且服务端拒绝执行。

### Phase 0：可观测性与兼容基础

实现状态：主要链路已完成。提取器会通过学生 SSE 推送 `extracting/no_change/changed/failed/discarded`，失败进入服务日志，学生端不再依赖回答后的固定延时轮询；内部指标和更细的失败分类仍待补充。

目标：先让当前异步提取可诊断，再改变产品语义。

- 为提取任务增加完成、无变化、失败日志和内部指标。
- 通过学生 SSE 推送提取状态，替代固定 1.5 秒、4.5 秒刷新。
- 增加数据库 migration 框架测试，为新字段和状态迁移做准备。
- 保持现有候选确认行为不变。

验收：能够区分没有候选、模型格式错误、超时、关闭后丢弃和存储失败；主对话仍不受影响。

### Phase 1：自然写入与轻提示

实现状态：部分完成。`adaptive` 模式已允许现有低敏感提取器的结果直接成为可用 Memory，自动写入后会显示非阻塞“已了解”提示并可一键撤销该条，学生也可查看、编辑和删除；结构化提案、确定性敏感规则、分类页面和变更审计尚未实现。

目标：普通表达即可形成低风险 Memory，不再要求逐条确认。

- 将提取器改为结构化提案，包含类型、置信度、敏感度、证据和操作。
- 实现确定性写入策略和敏感信息拒绝规则。
- 低风险高置信度提案自动设为 `active`。
- 对话区增加“已了解 + 撤销”提示。
- Memory Tab 改成“关于我”，`needs_review` 退居次要位置。
- 显式“记住/忘掉/纠正”作为强意图测试，但不作为普通流程前提。

验收：自然说出学习偏好后，无需额外确认即可在新对话生效；撤销后立即停止读取；敏感信息不落库。

### Phase 2：合并、纠正与稳定读取

实现状态：已开始。读取已从“任意中文二元词相交”改成有限候选评分：称呼、姓名等核心画像稳定召回，其余条目按词项相关度排序；每轮最多 5 条并受总 token 上限约束。同义语义重排、显式类型、使用统计和冲突合并仍待实现。

目标：Memory 随对话演进，而不是不断堆积。

- 提取时提供同类型现有画像，实现 add/update/supersede/forget。
- 增加重复、补充、冲突和明确纠正测试集。
- 本地相关性评分加入类型、最近使用和重要性。
- 每轮最多读取 5 条，并更新使用统计。
- 建立离线回放评测：写入准确率、漏检率、错误写入率、检索准确率和无关注入率。

验收：重复表达不新增条目；纠正旧信息后只使用新值；无关任务不注入画像。

### Phase 3：近期经历与语义检索评估

目标：在不污染长期画像的前提下支持跨 Tab 的阶段连续性。

- 增加带 TTL 的近期经历摘要。
- 用真实匿名课堂样本比较本地评分、小模型重排和 embedding 召回。
- 只有评测显示收益明确时才引入额外模型调用或向量索引。
- 评估单对话“临时模式”。

验收：近期任务能在新 Tab 延续，过期后自动退出上下文；延迟和成本满足 50 名学生并发约束。

## 十、测试与指标

### 自动测试

- 提取：自然表达、临时要求、敏感内容、提示注入、无候选、格式错误和超时。
- 写入：自动激活、待确认、重复合并、冲突、纠正、忘记、撤销和开关 revision 竞争。
- 隔离：学生、场次、对话和已结束 run 的严格隔离。
- 教师策略：三种 Memory 模式、Tool 交集、动态关闭、revision 竞争、未授权学生修改和既有场次兼容。
- 读取：相关、同义表达、无关输入、条数上限、token 上限和旧状态兼容。
- UI：SSE 状态、提示撤销、“关于我”分类、编辑删除和无障碍 Tab。
- 迁移：MVP 数据库升级后原有 confirmed/candidate 状态映射正确。

### 产品指标

- 自动写入接受率和撤销率。
- 每百轮错误写入、重复写入和冲突未处理数量。
- 相关 Memory 被成功读取的比例。
- 无关 Memory 被注入的比例。
- Memory 给主回答增加的 P50/P95 延迟与模型调用成本。
- 学生打开管理页面、编辑、删除和关闭 Memory 的频率。

不能只以“存了多少条”作为成功指标。更重要的是少存但准确、该用时能用、用错时容易纠正。

## 十一、实现落点

- `internal/agent/memory.go`：结构化提取、协调、写入策略和相关性评分。

- `internal/store/store.go`：schema migration、`run_policies`、Memory 字段、事件审计和原子撤销。
- `internal/server/server.go`、`handlers.go`：教师策略接口、有效 Tool 校验、SSE 状态、撤销和事件接口。

- `web/index.html`、`web/ui.css`：按课堂策略显示 Tool 和 Memory、轻提示、“关于我”和少量待确认区域。
- `internal/agent/engine_test.go`、`internal/store/store_test.go`、`internal/server/server_test.go`、`web/memory-ui.test.js`：分层验收。

## 十二、调研依据

- [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq)：区分 Saved Memory 与聊天历史，强调自动形成、相关读取、来源和用户控制。
- [Claude Memory Tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)：由 Agent 按需读写外部 Memory，存储仍由应用控制。
- [LangGraph Memory](https://langchain-ai.github.io/langgraphjs/how-tos/delete-messages/)：区分 thread 级短期历史与跨 thread 长期 Memory，并区分语义、经历和程序性记忆。
- [Generative Agents](https://arxiv.org/abs/2304.03442)：记录经历、生成反思，并按相关性、重要性和时间动态检索。
- [MemGPT](https://arxiv.org/abs/2310.08560)：把有限上下文视为工作集，在不同记忆层级之间按需移动信息。
- [CoALA](https://arxiv.org/abs/2309.02427)：将语言 Agent 组织为模块化 Memory、动作空间和决策过程。

## 十三、首个开发切片

首次实现建议先交付 Phase Policy 和 Phase 0，再加上 Phase 1 的最小纵向闭环：

1. 老师可以为当前场次选择三种 Memory 模式和允许的 Tool；
2. 服务端强制计算有效 Tool 交集，并通过 SSE 同步学生页面；
3. 提取状态可观察；
4. 新结构化提案但暂不做复杂语义合并；
5. 只允许 `preference`、`goal` 和 `learning_need` 自动激活；
6. 自动写入后展示“已了解 + 撤销”；
7. 其他类型继续进入 `needs_review`；
8. 保持现有读取算法和场次作用域；
9. 用固定评测样本验证后，再进入合并与检索升级。

这样可以先验证“无须说请记住”是否真正改善课堂体验，同时把数据迁移、召回算法和近期经历带来的风险隔离到后续阶段。
